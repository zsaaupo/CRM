# Sale ERP development roadmap for eManager

Verified on 24 November 2026 against `feature/enhanced` at `261c0fa`. Both supplied guides describe this commit. The reference screens and menu inventory come from the guides. The local findings below come from the checkout. Reference posting rules, including payable recognition, tax allocation and production waste, still require worked examples agreed with the business.

**First release target:** A cashier can complete a credit sale, record a later collection, and process a partial return. Stock, account history and customer due must agree after each action. The existing full-payment checkout must still pass its tests. Deliver this through the order page and API before adding a POS terminal.

## How to use the two guides

Use `SALE_ERP_GAP_IMPLEMENTATION_PLAN.md` for its reference-screen inventory, import columns and worked acceptance cases. Use `emanager_saleerp_gap_analysis_and_implementation_guide.md` for candidate models and endpoints. Four changes to its six-phase ordering matter for this checkout.

1. Move biller identity, checkout settings and the first audit events into the releases that write sales and payments. Adding these later would leave early transactions with missing provenance.
2. Bring receipt-level quantities and frozen pricing forward. POS discounts, supplier returns and historical reports all consume those values.
3. Schedule manufacturing after costed units and material replenishment. The team can deliver cash/card checkout while the business verifies BOM waste calculations.
4. Deliver reports as their data becomes reliable. Customer dues need return-adjusted settlement. Product margin also needs recorded issue cost. A report count alone gives neither report an acceptance criterion.

## First development backlog

1. **Baseline PR.** Use the documented Windows PDF setup in [report/README.md](report/README.md), declare the PDF reader as a test dependency, and run full discovery. Extend [finance tests](accounting/test_finance.py), [completion tests](sale/tests/test_completion.py) and [receiving tests](purchase/tests/test_receiving.py) only for missing legacy, FX and return fixtures.
2. **Settlement schema PR.** Introduce additive settlement mode and posting-command/allocation identity. Backfill existing payments with distinct stable identities. Migrate refund links, preserve transaction origins, then replace per-order purchase uniqueness. Check pre/post counts, links and balances. Derive payment status centrally, including zero-total and fully returned documents.
3. **Credit sale PR.** Implement deferred completion plus scoped collection through the existing sales payment collection route. Update order entry, detail and quote conversion. Test rollback, insufficient scope, duplicate-key replay and conflicting payloads. Preserve the existing response and full-payment behavior for legacy completion.
4. **Supplier and returns PR.** Add supplier payment history and installment commands. Apply return credit against open due first under the proposed policy, then allocate any refund against previous tenders. Cover split payments, concurrent installments, rounding and a restricted warehouse with a shared account. Enable the new UI only after sales and purchase returns reconcile.
5. **Inventory foundation PRs.** Add the journal and an opening-balance reconciliation command, then route receipt, issue, return and transfer writers through it. Use a consistent cutoff for opening balances. Make the journal and balance update one transaction. Run the existing concurrency and manual-stock-removal suites before enabling dependent features.

## Decisions and rollout

- **Before credit release:** Agree when purchase liability arises, how pending differs from due, how shipping and header discounts affect returns, and how overpayments are handled. Use the order's stored FX and record both document and base amounts where needed. Until partial receipts ship, the existing received-in-full event is a clear starting point.
- **Before valuation release:** Decide the opening-cost source and cost method. Moving weighted average per warehouse/SKU is a proposal. Mark missing historical costs explicitly. Agree on treatment of backdated events and negative stock before either can affect valuation.
- **Before later releases:** Obtain examples for inclusive tax and residual rounding, BOM Net/Gross waste and rejected output, register variance, and profit versus revenue. Each example becomes a test for the consuming feature.
- **Cutover:** On a restored copy, compare stock by warehouse/SKU, account balances by source, and dues by order before and after migration. Mark historical receipts and settled transfers as legacy evidence. Creating those markers must leave inventory and money untouched. At deployment, coordinate a cutoff across all stock writers, then pilot the new entry points in one warehouse. For rollback, disable those entry points and preserve recorded events for reconciliation or reversal.
